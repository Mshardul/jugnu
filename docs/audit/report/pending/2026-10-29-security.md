## Findings

### F1 — `cleanup.paths` deleted on uninstall with no containment

- **Severity:** Critical
- **Where:** `shell/Sources/JugnuCore/Cleanup.swift:32-37` (`performUninstall`), `expandHome` `:96-105`; schema `Models.swift:405-413`
- **What:** `addon.yaml` `cleanup.paths` entries go through `expandHome` then `FileManager.removeItem`. No check that the result sits under the addon's own state/config dirs. `~`, `~/Documents`, `/` all resolve and delete. Manifest id/version/hash gates do not look at this field.
- **Why it matters:** A hostile or compromised addon (sha256 only proves integrity of what the registry said) makes the user's *uninstall* click an arbitrary-delete primitive. Users treat uninstall as the safe action.
- **Existing ticket:** none (0024 is about completeness of cleanup, not its bounds)
- **Suggested direction:** resolve + standardize, require containment under the addon's state/config roots (or a small allow-listed set), reject otherwise at manifest load.

### F2 — Helper `id`/`version` unvalidated → path traversal

- **Severity:** Critical
- **Where:** `Models.swift:415-427` (`HelperRef`), `Paths.swift` `helperRoot(id:version:)`, `Cleanup.swift:50-62` (`removeOrphanedHelpers`), `AddonInstaller.swift` `commitHelperPackage`
- **What:** `ManifestLoader.load` validates the addon id but not `helpers[].id` / `.version`. `helperRoot` is plain `appendingPathComponent`. A manifest with `helpers: [{id: "..", version: ".."}]` makes `removeOrphanedHelpers` delete `~/.local/share` (two levels above `…/jugnu/helpers`). Install of the single-addon path commits the addon *before* `ensureHelpers` fails on "not in catalog", so the addon stays installed and enabled; uninstalling it then triggers the delete.
- **Why it matters:** same class as F1, reachable from a manifest alone.
- **Existing ticket:** none
- **Suggested direction:** validate helper id (same regex as addon ids) and version (semver) in `ManifestLoader`; also reject non-semver in `HelperManifest` decode; consider ordering helper resolution before the addon commit.

### F3 — `cleanup.launchd` labels unvalidated

- **Severity:** Major
- **Where:** `Cleanup.swift:12-19`, `Models.swift:484-490`
- **What:** `cleanup.launchd` labels are interpolated into `launchAgentsDir/<label>.plist` and passed to `launchctl bootout`/`unload`. `../../x` removes an arbitrary `*.plist`; a label like another addon's `com.jugnu.*` or a non-Jugnu agent gets booted out. Disable also runs this.
- **Why it matters:** cross-addon interference and arbitrary `.plist` delete from a manifest field.
- **Existing ticket:** related to 0023/0024 (too narrow: lifecycle correctness, not label trust)
- **Suggested direction:** require labels to match `com.<addon-id>.*` for the addon being cleaned; reject `/` and `..`.

### F4 — Registry fetch unconfined

- **Severity:** Major
- **Where:** `RegistryClient.swift:111-135`, `ShellConfig.registryURL` (`Models.swift:221`)
- **What:** `fetch`/`fetchHelpers` use `URLSession.shared` (follows redirects, any scheme incl. `http`, any host, no body-size cap). The registry is the sha256 root of trust, so a MITM on `http://` or a redirect swaps hash *and* URL; the install allowlist then only requires the (attacker-chosen) URL to be on github.com / githubusercontent, so an attacker-owned GitHub release passes.
- **Why it matters:** the install pipeline is carefully confined, its root of trust is not. Unsigned registry is a documented v0 non-goal, but `http` and unbounded response size are not documented.
- **Existing ticket:** related to 0028/0054 (no registry-trust ticket)
- **Suggested direction:** reuse `AllowlistedDownloadSession`-style https-only + redirect confinement for the registry; cap response size; longer-term: signed registry.

### F5 — Addon inherits Jugnu's full environment

- **Severity:** Major
- **Where:** `AddonRunner.swift:85-89`
- **What:** `var env = ProcessInfo.processInfo.environment` plus overlays. Any token in the launching environment (shell-started dev runs, launchd inheritance) reaches every addon.
- **Why it matters:** privacy rule in `docs/conventions.md` → Privacy and trust; widens blast radius of any third-party addon beyond what it declares.
- **Existing ticket:** related to 0021 (sandboxing), too narrow to cover env
- **Suggested direction:** allow-list env (`PATH`, `HOME`, `LANG`, `TMPDIR`, `USER`, plus `JUGNU_*`).

### F6 — `entrypoint.path` not confined

- **Severity:** Minor
- **Where:** `AddonRunner.swift` `spawn` (`addonRoot.appendingPathComponent(entrypoint.path)`)
- **What:** `..` segments can point outside the addon root. Mostly moot (addon already runs arbitrary code), but `PackageGates.checkEntrypoint` then inspects a file outside the package.
- **Existing ticket:** none
- **Suggested direction:** validate at manifest load: relative, no `..`.

### F7 — Daemon first-party gate is id-only

- **Severity:** Minor
- **Where:** `ManifestLoader.swift:38-40`, `FirstPartyDaemons.swift`
- **What:** `FirstPartyDaemons.ids` is a set of ids; nothing ties the id to a trusted publisher/registry entry. Today safe only because third-party registries do not exist yet.
- **Why it matters:** becomes a bypass the moment a non-first-party registry or local install is supported.
- **Existing ticket:** none

### F8 — Temp extract dir leaked on failure

- **Severity:** Minor
- **Where:** `AddonInstaller.swift` `downloadAndExtractAddon` (extractRoot removed only on success path)
- **What:** if `ZipExtractor.extract`/`findPackageRoot`/`copyItem` throws, `jugnu-extract-<UUID>` stays in the temp dir. Not a security hole; hygiene, and contrasts with the `defer` cleanup in sibling functions.

### F9 — Dev env switches live in Release

- **Severity:** Observation
- **Where:** `App/ScreenshotMode.swift:7,47`
- **What:** `JUGNU_SCREENSHOT_MODE=1` redirects `$HOME` to a temp dir and seeds addons; `JUGNU_REPO_ADDONS` points installs at a repo tree. Neither bypasses verify/permission gates as far as the inspected code shows, but they ship in the Release build. Confirm `JUGNU_REPO_ADDONS` goes through the verified install path.

### F10 — Static analysis blind spots

- **Severity:** Observation
- **Where:** `.github/workflows/ci.yml:semgrep`
- **What:** semgrep scans `addons/` only, with `python-logger-credential-disclosure` excluded; Swift in `shell/` (where F1–F5 live) has no security scan.

## Resolution (2026-10-30)

Fixed in the same pass, with tests (`swift test`: 342 pass):

- **F1, F2, F3, F6** — `ManifestLoader` now rejects unsafe `cleanup.paths`, `cleanup.launchd`, `helpers[].id/version`, `entrypoint.path`, and dependency ids (`PackageGates.validate*`). `Cleanup` expands `~` against the shell's home, not the process user's.
- **F4** — `RegistryTransport`: https (or `file` for local registries) only, redirects must stay https, body capped at 5 MB. Used by addon, helper, and app registry fetches.
- **F5** — `AddonRunner.childEnvironment` passes only `PATH HOME USER LOGNAME SHELL TMPDIR LANG LC_* __CF_USER_TEXT_ENCODING` plus the shell's own `JUGNU_*` overlays.

Still open: F7, F8, F9, F10; the registry is still unsigned (documented v0 non-goal); `scripts/validate-addon.sh` does not yet mirror the new manifest rules; an already-installed addon with a now-invalid manifest cannot be uninstalled through the UI.

### Follow-up (2026-10-30)

- **F8** fixed: `downloadAndExtractAddon` removes its extract dir with `defer`, so a failed extract no longer leaks it. No dedicated test (the path is reachable only through a dependency install plan).
- **F9** fixed: `ScreenshotMode.isActive` is `false` in Release builds, so `JUGNU_SCREENSHOT_MODE` and the unverified `JUGNU_REPO_ADDONS` copy only work in Debug (`scripts/screenshots.sh` already builds Debug). Both configurations build.
- **0028** done as badge-only (registry `trust` tier); the id-prefix badge checks are gone. **F7** (daemon gate still keyed on id) is now blocked only on signed zips.
- Still open: **F7** (needs signing), **F10** (CI has no Swift security scan; not changed because the new job could not be validated locally), unsigned registry (documented v0 non-goal).
